# 4Dアプリケーションにおけるエラー管理とログ記録

Karim Meghraoui（4D Morocco テクニカルサポートエンジニア）

テクニカルノート 25-09

## 概要

複雑なアプリケーションでは、ファイルの欠落や不安定なネットワーク接続から予期しないバグまで、さまざまな種類のエラーが必ず発生します。こうしたエラーは、一般にいくつかのカテゴリーに分けられます。言語の規則に違反したコードが原因で、通常はコンパイル時に検出される構文エラー。ゼロ除算のような不正な操作によって実行中に発生するランタイムエラー。プログラムは問題なく動作しているのに誤った結果を返す論理エラー。タイムアウトやサーバーに到達できないといった接続の問題で起こるネットワークエラー。そして、システムのメモリやファイルハンドルが不足したときに発生するリソースエラーです。

現代の4D開発ツールは、こうしたエラーを効率よく検出・分析・管理するための堅牢な手段を提供しています。これらのツールを組み込むことで、開発者は診断を容易にし、アプリケーションの安定性を保ち、スムーズなユーザー体験を実現できます。

## はじめに

デフォルトでは、エラーが発生すると処理をブロックするダイアログボックスが表示され、メソッド、行、エラーコード、メッセージといった技術的な詳細が示されます。この方法には、作業の流れが中断される、メッセージがわかりにくい、自動的に回復したりエラーをログに記録したりする手段がない、といったユーザーにとっての課題がいくつもあります。このテクニカルノートでは、従来の方法と新しい方法の両方でエラーを処理し、これらの課題に対処する方法を説明します。

## ON ERR CALL コマンドによる従来のエラー処理

**ON ERR CALL** コマンドは、エラーを一元的に、あるいは局所的に処理するための4Dの標準的な仕組みです。このコマンドを使用すると、独自のエラー処理ルーチン（エラー処理メソッド、ハンドラーとも呼ばれます）をインストールできます。インストールしたメソッドは、コードの実行中にエラーが発生すると自動的に呼び出されます。エラー処理メソッドは、次のシンタックスでインストールします：

```4d
ON ERR CALL("MethodName "; ek scope)
```

たとえば、グローバルなエラー処理メソッドをインストールするには、次のようにします：

```4d
ON ERR CALL("myGlobalErrorHandler"; ek global)
```

これを無効にするには、次のようにします：

```4d
ON ERR CALL(""); // or ON ERR CALL("", ek global)
```

このコマンドを有効にすると、エラーをインターセプト（横取り）できるだけでなく、表示するメッセージをカスタマイズしたり、エラーをログに記録したり、実行を続行するか中止するかを判断したりできるようになります。このエラー管理は、ローカル、グローバル、コンポーネントの3つのスコープで適用されます。

## ON ERR CALL コマンドの3つのスコープ

### 1. ローカルスコープ（ek local）

ローカルスコープでは、特定のコードブロックやメソッドに対してエラー処理メソッドを定義できます。この方法により、プログラムの特定の部分で発生しうるエラーを、的を絞って細かく制御できます。ローカルなエラー処理メソッドは、常に他の種類のエラー処理メソッドより優先されます。つまり、そのスコープ内でエラーがキャッチされた場合、最初に実行されるのはローカルなエラー処理メソッドです。

ファイルアクセス、データベース操作、ネットワーク通信などのデリケートな処理の前後では、ローカルスコープの使用を強くお勧めします。処理が完了したら、アプリケーションの他の部分に影響を与えないよう、**ON ERR CALL**($previousErrorHandler) で元のエラー処理メソッドを必ず復元してください。

### 2. グローバルスコープ（ek global）

グローバルスコープでは、ローカルなエラー処理メソッドが存在しないすべての実行コンテキストに適用されるエラー処理メソッドを定義できます。そのため、4Dアプリケーションのエラー管理を一元化するのに最適です。

このグローバルなエラー処理メソッドは、データベースの **On Startup** データベースメソッドでインストールすることをお勧めします。そうすることで、起動直後からエラー処理が有効になります。この種類のエラー処理メソッドは、ローカルで処理されていないすべてのエラーをキャプチャーするため、アプリケーションの一貫性と回復力を高めます。

### 3. コンポーネントスコープ（ek errors from components）

4Dでコンポーネントに関連するエラーの管理を強化するには、**ON ERR CALL** コマンドに ek errors from components スコープを指定して、ホストデータベースにグローバルなエラー処理メソッドをインストールします。このエラー処理メソッドは、コンポーネント自身が処理しなかったエラーだけをインターセプトします。したがって、コンポーネント内部のエラー処理メソッド（存在する場合）を置き換えるものではなく、それを補完するものです。

この設定は、コンポーネントの実行コンテキストで4D標準のエラーダイアログボックスが表示されるのを防ぐのに特に役立ちます。動作がより予測しやすくなり、ホストデータベースの堅牢性が向上し、コンポーネントに関連する異常を一元的に管理できるようになります。

この仕組みを有効にするには、次のコマンドでコンポーネント専用のエラー処理メソッドをインストールする必要があります：

```4d
ON ERR CALL("myComponentErrorHandler"; ek errors from components)
```

## 実践例：読み取り専用ファイルへの書き込みエラー

データベースフォルダーにある example.txt というファイルに書き込みを試みるメソッドを考えます。このファイルはあえて読み取り専用に設定してあるため、書き込みはできず、「Access Denied」（アクセス拒否）エラーが発生します。

この状況での4Dコードの動作を、**ON ERR CALL** コマンドでエラー処理メソッドを有効にした場合と、有効にしない場合の両方で確認します。

```4d
var $error; $colJSON : Collection
var $fileContent : Text
var $created : Boolean
var $obFile : Object
var $previousErrorHandler : Text

$previousErrorHandler:=Method called on error

LOG EVENT(Into 4D diagnostic log; Localized string("LogRuntimeError"); Error message)
var $fileHandle : 4D.FileHandle:=Folder(Database folder).file("example.txt").open()

If ($fileHandle#Null)
    ON ERR CALL("ErrorWriteDoc")
    $previousErrorHandler:=Method called on error
    $fileHandle.writeLine("hello")
End if
```

### ケース1：ON ERR CALL を使用しない場合

**ON ERR CALL** コマンドを使用しないと、エラー（読み取り専用ファイルへの書き込みなど）が発生するとすぐに4Dのシステムダイアログボックスが表示されます。ユーザーは「中止」「続行」「トレース」「編集」のいずれかをクリックしなければならず、この操作が行われるまでコードの実行は一時停止します。

メソッドを呼び出すと：

```4d
$fileHandle.writeLine("hello")
```

4Dはシステムエラーを発生させます。ダイアログボックスが表示され、実行が中断されます。

![](fig-01)

ユーザーは（中止、続行などの）選択を迫られ、処理が手動の操作に依存することになります。

### ケース2：ON ERR CALL("ErrorWriteDoc") を使用する場合

4Dでは、**ON ERR CALL("ErrorWriteDoc")** コマンドで、エラーを一元的に処理するメソッドをインストールできます。エラーが発生すると ErrorWriteDoc メソッドが自動的に呼び出され、コードの実行をブロックすることなく問題を処理します。

```4d
$error:=Last errors
If ($error.length=0)
    $error:=[{}]
End if
$error[$error.length-1].time:=String(Current date)+" "+String(Current time)
$error[$error.length-1].app:=Application info
$error[$error.length-1].version:=Application version
$error[$error.length-1].os:=System info.osVersion
$error[$error.length-1].method:=Error method
$error[$error.length-1].line:=Error line
$error[$error.length-1].formula:=Error formula
$obFile:=Folder(fk logs folder).file("errors.json")
If (Not($obFile.exists))
    $created:=$obFile.create()
    If (Not($created))
        LOG EVENT(Into 4D diagnostic log; Localized string("LogErrorFileCreationFailed"); Error message)
    End if
    $colJSON:=[]
Else
    $fileContent:=$obFile.getText()
    If ($fileContent#"")
        $colJSON:=JSON Parse($fileContent)
    Else
        $colJSON:=[]
    End if
End if
$colJSON.push($error)
$obFile.setText(JSON Stringify($colJSON; *))
//ALERT("Write Error !")
```

このメソッドは、まず Last errors で直近のエラーを取得します。次に、最新のエラーに役立つコンテキスト情報を追加します。Error method はエラーが発生したメソッドの名前、Error line はその行番号、Error formula はエラーを含むコードの行を示します。これらの情報により、コード内で問題が起きた正確な場所を特定できます。

ほかにも、日付、時刻、アプリケーションのバージョン、システムのバージョンなどの情報を追加します。これらをすべて、エラーログとして使用する errors.json ファイルに保存します。ファイルがすでに存在する場合はその内容を更新し、存在しない場合は自動的に作成します。

## エラー処理メソッドの実行順序

4Dはエラーが発生すると、厳密な優先順位に従って呼び出すエラー処理メソッドを決定します：

1. ローカルなエラー処理メソッド（ek local）が定義されている場合は、それが最初に実行されます。
2. そうでない場合、エラーがコンポーネントから発生したものであれば、コンポーネント用のエラー処理メソッド（ek errors from components）が呼び出されます。
3. それ以外の場合は、グローバルなエラー処理メソッド（ek global）が処理を引き継ぎます。
4. エラー処理メソッドが1つもインストールされていない場合は、4Dがシステムエラーダイアログを表示します。

この優先順位により論理的な順序が保たれ、同じアプリケーション内で複数のレベルのエラー処理を競合なく組み合わせることができます。

## 現在のエラー処理メソッドの取得

4Dで **ON ERR CALL**("MethodName") コマンドを使用すると、独自のエラー処理メソッドが有効になります。つまり、その後でエラーが発生すると、4Dはシステムエラーを表示する代わりに、指定されたメソッドを自動的に呼び出してエラーを処理します。

ただし、すでに別のエラー処理メソッドが設定されていた場合は、新しいメソッドを有効にする前に、それを保存しておくことが重要です。そうすれば、現在の処理が終わったときに元のメソッドを復元でき、アプリケーションの他の部分に影響を与えずに済みます。

そのためには、**Method called on error** コマンドを使用します。このコマンドは、現在有効なエラー処理メソッドの名前（設定されていない場合は空の文字列）を返します。たとえば、次のように変数に保存します：

```4d
$previousErrorHandler := Method called on error
```

その後、**ON ERR CALL**("MyMethod") で別のエラー処理メソッドを一時的に有効にし、ファイルへの書き込みなどのデリケートな処理を実行します。最後に、次のように元のエラー処理メソッドを復元します：

```4d
ON ERR CALL($previousErrorHandler)
```

この行により、最初に有効だったエラー処理メソッドがそのまま復元されます。事前に何も定義されていなかった場合は、変数に空の文字列が入っているため、エラー処理メソッドは自動的に無効になります。

こうすることで、コードの信頼性が保たれ、独自のエラー処理を実装しているかもしれないアプリケーションの他の部分に干渉することもありません。

**Method called on error** コマンドには任意の引数を指定でき、グローバルなエラー処理メソッドやコンポーネント用のエラー処理メソッドも取得できます。

ローカルなエラー処理の場合：

```4d
$localHandler:=Method called on error
```

グローバルなエラー処理の場合：

```4d
$globalHandler:=Method called on error(ek global)
```

コンポーネントのエラー処理の場合：

```4d
$componentHandler:=Method called on error(ek errors from components)
```

## エラースタック

**Last errors** コマンドを使用すると、4Dアプリケーションの現在のエラースタックを取得できます。このコマンドはオブジェクトのコレクションを返します：

各オブジェクトが1つのエラーに対応し、エラー番号、関連するメッセージ、エラーの原因となった内部コンポーネントの署名などの情報を持っています。エラーが記録されていない場合、このコマンドは null を返します。

**throw** コマンドで明示的に生成したエラーも、スタックに含めることができます。

このコマンドは、**ON ERR CALL** でインストールしたメソッドの中や、**Try** または **Try/Catch** ブロックの中など、エラー処理に適したコンテキストで使用する必要があります。

## エラーの中止

どのエラー処理メソッドが実行される場合でも、**ABORT** コマンドは常に有効で、コードの実行を停止できます。

**ABORT** コマンドは、**ON ERR CALL** で定義したエラー処理用のプロジェクトメソッドの中で使用するためのものです。エラー処理メソッドがインストールされていない場合、4Dは標準のエラーダイアログを表示し、コンテキスト（フォーム、メニュー、プロセスなど）に応じて実行を中断します。

一方、エラー処理メソッドが定義されている場合、4Dはダイアログボックスを表示せず、エラー処理メソッドを呼び出した後も実行を続けます。そのため、一部のエラーはプログラムで処理できます。重大なエラーや回復できないエラーの場合は、**ABORT** コマンドを呼び出して、4Dがデフォルトで行うのと同じように実行を適切に停止することをお勧めします。

*注：ABORT コマンドを他のコンテキストで使用する例も見られますが、公式にはエラーをインターセプトするプロジェクトメソッドでの使用に限られています。*

## 4Dにおける新しいエラー処理

4D 20 R2 以降、**throw()** コマンドを使用すると、コードの任意の位置で手動でエラーを生成できます。このコマンドはエラーコードやカスタムメッセージを受け取り、4Dの標準エラーと同じように動作します：

- エラー処理メソッド（**ON ERR CALL**）が定義されていない場合は、ダイアログボックスが表示されます。
- 定義されている場合は、指定されたメソッドがエラーをキャプチャーします。

この機能により、エラーの事前検出、ログ記録、構造化されたエラー処理が容易になります。

### コードとメッセージを指定してすぐにエラーをスローする

**throw(code; message)** コマンドは、その場でエラーを発生させます。このエラーは：

- **ON ERR CALL** のメソッドでキャッチできます。
- エラー処理メソッドが有効でない場合は、エラーダイアログを表示します。

これにより、コード内の例外的なケースを明確に知らせることができます。

簡単な例として、ゼロ除算を取り上げます。次のコードは、除数がゼロ（null）のときにエラーを生成し、便宜的にゼロを返す割り算のメソッドです。

```4d
#DECLARE($dividend : Real; $divisor : Real)->$result : Real
If ($divisor=0)
    $result:=0
    throw(-12345; Localized string("ErrorDivisionByZero"))
Else
    $result:=($dividend/$divisor)
End if
```

`throw(-12345; Localized string("ErrorDivisionByZero"))`

この命令は、コード -12345、メッセージ "Division by zero!"（日本語環境では「ゼロによる除算です！」）のエラーを発生させます。メッセージは **Localized string** コマンドで XLIFF ファイルから取得するため、アプリケーションの言語に応じて切り替わります。

**ON ERR CALL** でエラー処理メソッドが定義されていれば、そのメソッドが呼び出されてエラーを処理します。

- そうでない場合、4Dは標準のエラーダイアログボックスを自動的に表示し、コード -12345 とメッセージ "Division by zero!" という独自の情報を示します（下のスクリーンショット）。標準のエラー表示は次のとおりです。

### プロパティを持つオブジェクトでエラーをスローする throw(errorObj)

errorObj オブジェクトを使用すると、より詳細にカスタマイズしたエラー処理ができます。このオブジェクトには、次のプロパティを指定できます：

- **componentSignature（テキスト）：** エラーの発生元を示す4文字の署名。デフォルトでは、ホストデータベースの場合は "host"、コンポーネントの場合は "C001"、"C002"… です。
- **errCode（数値）：** エラーコード。省略した場合は -1 です。
- **message（テキスト）：** エラーの説明。プレースホルダー（例：{propertyName}）を含めることができます。空または省略した場合は、XLIFFファイルから ERR_{componentSignature}_{errCode} という名前のメッセージが検索されます。
- **deferred（ブール）：** true の場合、エラーはメソッドまたは Try ブロックの終わりまで遅延されます（デフォルト：false）。

同じメソッド内でこのコマンドを複数回実行し、複数のエラーを生成することもできます。deferred オプションを有効にすると、それらのエラーをまとめて一度に返すことができます。

### 遅延エラー処理

遅延モード（deferred）を使用すると、エラーの発生をメソッドまたは Try ブロックの終わりまで遅らせることができます。

- アプリケーションで **ON ERR CALL** のエラー処理メソッドが定義されている場合、メソッドの終わりにそれが自動的に呼び出されます。
- コンポーネントでは、遅延エラーのスタックをホストアプリケーションに渡すことができ、ホスト側で独自のエラー処理メソッドを実行します。

**Last errors** コマンドでこのスタックを取得し、遅延モードで発生したすべてのエラーを分析できます。

### 新しい Try() キーワードと、新しい Try、Catch、End try キーワードの紹介

4D 20 R4 と 4D 20 R5 以降、4Dランゲージにはランタイムエラーを処理する新しい方法が加わりました。この進化の中心となるのは、次の2つの主要な機能です：

- 4D 20 R4 で導入された **Try(expression)** 文では、エラーが発生しても実行をブロックせずに処理を試みることができます。
- 4D 20 R5 で導入された **Try...Catch** ブロックでは、Try ブロック内でスローされた例外を自動的にキャプチャーし、わかりやすい構造でエラーを処理できます。

この2つのツールは、エラーの回復と分析に中心的な役割を果たす **Last errors** コマンドに依存しています。

### Try および Try Catch での Last errors の使用

**Last errors** は、4Dの現在のエラースタックをエラーオブジェクトのコレクションとして返します。エラーが発生していない場合は Null を返します。

- エラースタックには、throw コマンドで送られたオブジェクトも含まれます（該当する場合）。
- このコマンドは、**ON ERR CALL** コマンドでインストールしたエラーコールバックメソッドの中、または **Try** や **Try/Catch** のコンテキストで呼び出す必要があります。

このコレクションの各エラーオブジェクトには、次のような有用な情報が含まれています：

- **errCode（数値型）**：エラーコード
- **message（テキスト型）**：エラーの説明
- **componentSignature（テキスト型）**：エラーを返した内部コンポーネントの署名

#### ユースケース1：新しい Try(expression) キーワードの使用

この例では、**Try(expression)** 文を使用して、**example.txt** というテキストファイルを開いて書き込みを試みます。このファイルは、意図的にエラーを起こすために読み取り専用に設定してあります。コードはまず、Try で囲んでファイルを開こうとします。開くことに成功すると FileHandle オブジェクトが返されます。失敗すると Try は Null を返し、エラーは自動的に **Last errors** に記録されます。

```4d
var $fileHandle : 4D.FileHandle:=Try(Folder(Database folder).file("example.txt").open())
If ($fileHandle#Null)
    Try($fileHandle.writeLine("Hello"))
End if
If (Last errors#Null)
    ErrorWriteDoc
End if
```

ファイルが読み取り専用のため書き込みは失敗し、エラーは **Last errors** に返されます。このコマンドを使用すると、エラーをコレクションとして取得できます。**Last errors** が空でなければ、エラーを処理するメソッドを呼び出します（この例で呼び出しているのは **ErrorWriteDoc** メソッドです）。

#### ユースケース2：新しい Try、Catch、End try キーワードの使用

2つ目の例では、4D 20 R5 以降で使用できる **Try...Catch** ブロックで、構造化されたエラー処理を行います。この構造では、複数の命令を Try ブロックで囲み、発生したエラーを Catch ブロックですぐにキャプチャーできます。この例では、**throw** コマンドで意図的にエラーを生成しています。エラーが発生するとすぐに **Try** 内のコードは停止し、プログラムは Catch ブロックに直接移ります。そこで **Last errors** を取得し、コレクションに追加します。次に、最初のブロックの中で2つ目の **Try...Catch** ブロックを使用して、別のエラーをスローします。最終的に、コレクションには2つのエラーが含まれます。この例から、プログラムを停止させずに複数のエラーを処理する方法と、**Last errors** を使ってそれぞれのエラーを記録する方法がわかります。

```4d
var $errors : Collection
$errors:=New collection()
Try
    throw(123; Localized string("ErrorFirst"))
    ALERT(Localized string("AlertNotExecuted"))
Catch
    $errors.push(Last errors)
    Try
        throw(456; Localized string("ErrorSecond"))
    Catch
        $errors.push(Last errors)
        // $errors collection contains the two previous errors
    End try
End try
```

この処理が終わると、**$errors** コレクションには、それぞれの **Catch** ブロックで取得した2つのエラーオブジェクトが含まれます。これらのオブジェクトには、**エラーコード**、**開発者が定義したメッセージ**、**エラー名**などの情報が含まれます。これにより、プログラムを中断せずにエラーをキャプチャーできるだけでなく、エラーを正確に追跡し、後で分析やログ記録に使うために保存することもできます。

![](fig-06)

このように、**Try(expression)** と **Try...Catch** ブロックのどちらを使う場合でも、**Last errors** コマンドはエラーを特定・取得・活用するための中心的な要素です。前者では手動で問い合わせる必要があり、後者では Catch ブロックの中でキャプチャーしたエラーを取り出すために自然に使用します。4Dのエラー処理がこのように近代化されたことで、コードはより読みやすく、より堅牢になり、何よりも現代的なプログラミング言語の標準に沿ったものになりました。

## まとめ

4Dの新しいエラー処理は、エラーを管理するための包括的で柔軟なツール群を提供します。**ON ERR CALL**、**throw()**、**Try** と **Try/Catch** を使用することで、開発者はエラーの流れを正確に制御し、問題を発生源で切り分け、クリーンで読みやすいコードベースを維持できます。これらの仕組みは詳細なログ記録をサポートし、ローカル、グローバル、コンポーネントのどのコンテキストでも一貫した処理を可能にし、手動の操作への依存を減らします。これらの手法を取り入れることで、アプリケーションはより堅牢になり、デバッグや保守も容易になり、ミッションクリティカルな環境でも4Dソリューションを確実にスケールさせることができます。
